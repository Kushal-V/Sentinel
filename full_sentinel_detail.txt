================================================================================
 1. PROJECT OVERVIEW
================================================================================

Sentinel is a Supply Chain Digital Twin — a multi-agent LLM orchestration
system that uses specialist AI agents to respond to supply chain crises in
real time. It combines:

  - Three persona-driven specialist agents (Maker, Mover, Keeper)
  - A structured-output Dispatcher that routes crises to the right agent
  - A Shadow Sandbox ("Imagination Room") that prevents hallucinated state
    changes from corrupting live data
  - A Retrospective Weighting system (trust scores) that dynamically adjusts
    agent routing over time based on past performance
  - A Two-Phase Commit protocol with Human-in-the-Loop (HITL) approval
  - A Dynamic Schema Inference Engine for multi-tenancy across any industry

The system is designed to be domain-agnostic: the same engine works for toy
factories, hospitals, shipping fleets, server farms, pharmaceutical warehouses,
electronics manufacturing, food cold chains, automotive parts, and retail
apparel — all without code changes.

================================================================================
 2. NOVELTY CLAIMS
================================================================================

CLAIM A — Shadow Sandbox (Hallucination Guard)
----------------------------------------------
Every proposed state change from an LLM agent is validated inside an isolated,
deep-copied DataFrame clone before any live data is touched. The sandbox
enforces two classes of constraints:

  (i)  Universal floor: no physical quantity can go below zero
  (ii) Dynamic ceiling: mutable columns cannot exceed their inferred limit
       column (e.g., current_stock <= max_capacity)

If a proposal violates any constraint, the sandbox returns a detailed rejection
message including the exact violated constraint, the numeric values, and the
maximum allowable change — enabling the LLM to self-correct.

CLAIM B — Retrospective Weighting (Trust Override)
---------------------------------------------------
After the LLM Dispatcher selects an agent, the orchestrator reads live trust
scores from persistent storage. If the chosen agent's trust score falls below
the ROUTING_THRESHOLD (default 0.50), the routing decision is programmatically
overridden to the agent's configured fallback. This override is:

  - Deterministic (not LLM-dependent)
  - Auditable (original_llm_choice is preserved)
  - Adaptive (the Analyst agent periodically reviews the transaction ledger
    and adjusts trust scores based on financial outcomes)

4.1 Core Pipeline Flow
----------------------

  [1] Crisis Event arrives
      (user-triggered via preset/custom text, or auto-detected by Scanner)
          |
          v
  [2] Dispatcher (Groq, llama-3.1-8b-instant)
      - Classifies crisis type (production/logistics/inventory)
      - Routes via with_structured_output(DispatchRoute)
      - Outputs strict JSON — no free-text allowed
          |
          v
  [3] Trust Override Check (Claim B)
      - Reads agent trust scores from FactoryDataManager
      - If chosen agent score < ROUTING_THRESHOLD (0.50):
        -> Override to preferred_fallback agent
        -> Set trust_override_applied = True
        -> Preserve original_llm_choice for audit
          |
          v
  [4] Specialist Agent (Groq, llama-3.3-70b-versatile)
      - Manual ReAct tool-calling loop (not create_react_agent)
      - Up to 10 iterations of think → tool_call → observe → think
      - XML <function=...> error recovery for Groq/Llama bug
          |
          v
  [5] Shadow Sandbox Validation (Claim A)
      - Every propose_state_change goes through ShadowSandbox
      - Deep-copied DataFrame clone prevents live data corruption
      - Checks: floor >= 0, ceiling <= inferred limit column
      - Returns SAFE or REJECTED with detailed explanation
          |
          v
  [6] Two-Phase Commit (HITL Approval)
      - SAFE proposals are STAGED in pending_changes list
      - Changes are NOT committed until human clicks "Approve & Execute"
      - On approval: re-validates each change against CURRENT state
        (guards against stale deltas)
      - On rejection: all staged changes discarded
          |
          v
  [7] Analyst (Trust Score Updater)
      - Reviews transaction_log.csv for financial outcomes
      - Applies trust score deltas based on evaluation criteria
      - Clamped to [-0.15, +0.15] per evaluation
      - Updates agent_trust_scores.json

5.4 src/core/schema_engine.py — Dynamic Schema Inference Engine
----------------------------------------------------------------
Lines: ~537

Classes:
  - ConstraintRule (frozen dataclass)
    Fields: mutable_column, limit_column, min_value (always 0.0)
  - SchemaProfile (dataclass)
    Fields: primary_key_column, numeric_columns, constraint_rules,
            column_dtypes, unconstrained_numeric_columns
    Method: as_agent_summary() — LLM-readable schema string
  - DynamicSchemaInferencer
    Takes any pandas DataFrame and extracts structural rules

Algorithm (3-phase):

  Phase 1: Primary Key Detection
    - Regex patterns tried in priority order:
      \bid\b, \bkey\b, \bsku\b, \bref\b, \bcode\b, \bname\b, \bslug\b
    - Fallback: first non-numeric column
    - Last resort: first column

  Phase 2: Constraint Pair Detection (same-stem matching)
    - For each numeric column, extract its stem:
      "current_stock" → "stock", "beds_occupied" → "beds",
      "active_compute_tb" → "compute"
    - Try each stem against _LIMIT_SUFFIX_PATTERNS:
      max_{stem}, {stem}_max, max_{stem}_{suffix},
      {stem}_{limit|cap|capacity|ceiling|total|size|maximum|upper|allowance}
    - First match wins; column pairs are recorded as ConstraintRules

  Phase 3: Cross-Stem Pair Detection (data-driven validation)
    - For unmatched columns: identify limit-looking columns via regex
    - For each candidate pair, compute the fraction of rows where
      mutable_value <= limit_value
    - If fraction >= 0.75 (_CROSS_STEM_MIN_RATIO), record the pair
    - Handles cases like containers_loaded/teu_limit, units_on_floor/stockroom_limit

Stem Extraction:
  - Strips prefixes: currently, current, curr, used, occupied, in_use, active
  - Strips suffixes: level, used, occupied, in_use, on_hand, qty, quantity,
    count, loaded, admitted, _tb, _gb, _kb
  - Skips columns that look like limits themselves (max_, _capacity, etc.)

5.5 src/core/sandbox.py — Shadow Sandbox (Claim A)
----------------------------------------------------
Lines: ~362

Classes:
  - SandboxResult (dataclass)
    Fields: status ("SAFE"/"REJECTED"), validated_state, rejection_reason,
            proposed_value, current_value, limit_value
  - ShadowSandbox
    Attributes: _shadow_df (deep copy), _profile (SchemaProfile)

evaluate_proposal(row_primary_key, target_column, delta) pipeline:

  Stage 1: Input validation
    - Row exists? (checks primary key column)
    - Column exists?
    - Column is numeric?
    - Current value is not NaN?
    → Rejection with valid keys/columns listed

  Stage 2: Apply delta to fresh clone (never mutate _shadow_df)
    - current_value + delta = proposed_value

  Stage 3: Universal floor constraint
    - If proposed_value < 0 → REJECTED
    - Message includes: delta, current, proposed, "minimum allowed = 0"

  Stage 4: Dynamic upper-bound constraint
    - Find applicable ConstraintRule for target_column
    - If limit column exists and proposed_value > limit_value → REJECTED
    - Message includes: delta, current, proposed, limit_column name, limit_value,
      maximum allowable increase

  Stage 5: All passed → SAFE
    - Apply delta to sandbox copy
    - Return validated snapshot DataFrame

Thread Safety:
  - Each evaluate_proposal operates on a freshly-cloned copy
  - Stateless across calls — concurrent Streamlit callbacks cannot interfere

5.7 src/tools/tool_registry.py — LangChain Tool Registry
----------------------------------------------------------
Lines: ~785

Singleton Pattern:
  - _data_manager module-level reference
  - set_data_manager(dm) / get_data_manager() for session sync
  - app.py calls set_data_manager(ss.manager) on every Streamlit rerun

Tool 1: get_dataset_schema()
  - MUST be called first by every agent
  - Returns SchemaProfile.as_agent_summary() plus:
    - All primary key values (up to 60)
    - Categorical column sample values (up to 15 per column)
    - First 3 sample rows
  - Enables agents to learn column names dynamically

Tool 2: query_data(search_term)
  - Case-insensitive substring search across ALL string/object columns
  - Fallback: splits multi-word searches into individual words
  - Returns matched rows as JSON list of dicts
  - If no matches: lists all available primary key values

Tool 3: propose_state_change(row_key, target_column, delta, justification)
  - The ONLY tool that can mutate live data
  - 4-stage pipeline:
    (1) Column validation (exists? numeric?)
    (2) Shadow Sandbox evaluation
    (3) Stage for HITL approval (append to pending_changes)
    (4) Audit logging (rejections logged for Analyst review)
  - Financial impact estimation via unit_cost column detection
  - Returns JSON on SAFE: status, row_key, column, old_value, new_value,
    delta, limit_value, justification, financial_impact_usd
  - Returns rejection text on REJECTED

Tool 4: ask_other_agent(target_agent, question)
  - Inter-agent communication for cross-domain actions
  - Creates a temporary ChatGroq client with llama-3.1-8b-instant
  - Sub-agent gets CONSULTATIVE override (no propose_state_change)
  - Sub-agent can only use get_dataset_schema and query_data
  - Runs a 5-iteration ReAct loop for the consultation
  - Returns text recommendation (Yes/No with justification)

Two-Phase Commit Functions:
  - commit_pending_changes() → re-validates each staged change against
    CURRENT state, applies valid ones, logs transactions, keeps failed ones
  - discard_pending_changes() → clears all staged changes

Groq XML Recovery:
  - parse_groq_xml_tool_call(error_str) → extracts tool name + args from
    Groq/Llama <function=name>args</function> XML error format
  - Fallback heuristic for kwarg-style strings

Exported Registries:
  - SENTINEL_TOOLS = [get_dataset_schema, query_data, propose_state_change, ask_other_agent]
  - INFO_TOOLS = [get_dataset_schema, query_data] (read-only for informational queries)

 6. AGENT SYSTEM DESIGN

6.1 Agent Personas
-------------------

MAKER (Chief Production & Supply Specialist)
  Domain: Manufacturing, production bottlenecks, raw material shortages,
          equipment failures, supply-side problems
  Fallback: Mover
  Personality: Analytical production engineer focused on throughput

MOVER (Head of Logistics & Distribution)
  Domain: Shipping delays, port strikes, transport disruptions, route changes,
          freight cost spikes, delivery failures
  Fallback: Keeper
  Personality: Speed-obsessed logistics expert focused on lead-days and cost

KEEPER (Inventory & Capacity Manager)
  Domain: Warehouse overflow, storage capacity warnings, inventory holding costs,
          stock discrepancies, reallocation needs
  Fallback: Maker
  Personality: Methodical, stingy, hates waste and over-stocking

ANALYST (Performance Intelligence Layer)
  Domain: Trust score evaluation, financial outcome review
  No tools: reads transaction ledger directly in prompt context
  Personality: Cold, data-driven mathematician with no loyalty to any agent

SCANNER (Risk Detection Pipeline)
  Domain: Proactive crisis detection from inventory data
  Runs per agent persona (Maker/Mover/Keeper perspectives)
  Output: Structured ScannerResult with list of CrisisEvent objects

6.2 Agent Tool Call Contract
-----------------------------
All agents MUST follow this mandatory order (enforced by prompts):

  Step 1: get_dataset_schema()
    → Learn column names (they vary per tenant/dataset)

  Step 2: query_data(search_term)
    → Read current values before proposing changes

  Step 3: propose_state_change(row_key, target_column, delta, justification)
    → Sandbox-gated, stages for HITL approval
    → If REJECTED: read rejection reason, recalculate, retry (up to 3 times)

  Optional: ask_other_agent(target, question)
    → Cross-domain consultation before acting

6.3 ReAct Tool Loop Implementation
------------------------------------
Instead of LangChain's create_react_agent (which breaks on Groq), the
orchestrator implements a manual ReAct loop:

  1. Build message list: SystemMessage + chat_history + HumanMessage
  2. Call llm_with_tools.invoke(messages) → AIMessage
  3. If AIMessage has tool_calls:
     a. Execute each tool via tool_map
     b. Append ToolMessage results to message list
     c. Yield step dicts for UI rendering
     d. Continue to next iteration
  4. If no tool_calls: this is the final answer → yield and break
  5. Maximum 10 iterations to prevent infinite loops

Error Recovery:
  - Groq/Llama XML bug: parse <function=name>args</function> from error string
  - Qwen3 reasoning: strip <think>...</think> blocks from content
  - Structured content blocks: extract text from dict/list message content

6.4 Mitigation Proposal Format
-------------------------------
All specialist agents must produce final answers in this format:

  --- MITIGATION PROPOSAL ---
  AGENT: [Maker/Mover/Keeper]
  CRISIS: [1-line summary]

  ACTIONS TAKEN:
    - [SKU/Item]: [column] changed from [old] → [new] ([delta]) — [reason]

  FINANCIAL IMPACT: [estimated cost/saving in USD]

  RATIONALE: [2-3 sentences with domain reasoning and actual numbers]

  SUGGESTIONS FOR THE OPERATOR:
    1. [Actionable recommendation]
    2. [Alternative approach]
    3. [Monitoring/follow-up needed]

  RECOMMENDED EMAIL DRAFT:
  Subject: [Crisis Type] — Mitigation Plan Requires Approval
  [professional 3-4 line email]
  --- END PROPOSAL ---

 7. MULTI-TENANCY VIA SCHEMA INFERENCE
================================================================================

The DynamicSchemaInferencer makes Sentinel work with any CSV dataset without
code changes. It has been tested across 5+ industry domains:

Domain                | Primary Key   | Mutable Column        | Limit Column
--------------------- | ------------- | --------------------- | ---------------------
Toy Factory           | item_id       | current_stock         | max_capacity
Hospital              | ward_id       | currently_admitted    | max_bed_capacity
Shipping Fleet        | vessel_id     | containers_loaded     | teu_limit
Server Farm           | rack_id       | active_compute_tb     | max_compute_allowance
Retail Apparel        | sku           | units_on_floor        | stockroom_limit
Pharmaceutical        | drug_id       | current_stock         | max_capacity
Electronics           | part_id       | current_stock         | max_capacity
Food Cold Chain       | item_id       | current_stock         | max_capacity
Automotive Parts      | part_number   | quantity_on_hand      | (unconstrained)

The inference engine handles:
  - Different primary key naming conventions (id, key, sku, ref, code, name)
  - Same-stem constraint pairs (current_stock ↔ max_capacity)
  - Cross-stem pairs with no shared word (containers_loaded ↔ teu_limit)
  - Unit suffixes in column names (_tb, _gb, _kb for compute resources)
  - Data-driven validation: cross-stem pairs require >= 75% of rows to
    satisfy mutable <= limit

 11. SECURITY & SAFETY CONSIDERATIONS
================================================================================

  - Path traversal protection: workspace names validated against "../" and "/"
  - Resolved path check: workspace directory must be under WORKSPACES_DIR
  - No SQL injection: all data operations via Pandas DataFrames
  - No command injection: no shell commands executed from user input
  - HTML escaping in Streamlit output (html.escape for agent messages)
  - Thread-safe writes: threading.Lock guards all file mutations
  - Atomic file writes: temp file + rename pattern prevents corruption
  - Sandbox isolation: deep copies prevent live data corruption
  - API key validation: GROQ_API_KEY required before any LLM call
  - Trust score bounds: clamped to [0.0, 1.0] to prevent runaway values
  - Financial guardrails: MAX_SINGLE_TRANSACTION_USD = $100,000

================================================================================
 13. DESIGN PATTERNS & ENGINEERING DECISIONS
================================================================================

  1. Singleton-per-Session: FactoryDataManager and AgentOrchestrator live in
     st.session_state to survive Streamlit's re-run model.

  2. Settable Singleton for Tools: tool_registry uses a module-level
     _data_manager reference synced via set_data_manager() on every rerun,
     ensuring tools always operate on the correct session's data.

  3. Manual ReAct Loop: LangChain's create_react_agent breaks on Groq's
     tool calling, so a custom loop handles the think→act→observe cycle.

  4. XML Error Recovery: Groq/Llama models sometimes emit <function=name>
     XML instead of JSON tool calls. The error string is parsed to extract
     the intended tool call and execute it anyway.

  5. Schema Inference over Configuration: Instead of requiring users to map
     columns manually, regex heuristics + data validation automatically
     discover the structure. This is the core multi-tenancy enabler.

  6. Two-Phase Commit: Agent proposals are never auto-committed. They are
     staged and require human approval, with re-validation at commit time
     to catch stale deltas.

  7. Deep Copy Everywhere: get_inventory() always returns a deep copy.
     ShadowSandbox deep-copies on init. Evaluation uses fresh clones.
     This prevents any accidental mutation of live state.

  8. Append-Only Audit Ledger: transaction_log.csv is never truncated during
     normal operation (only on dataset reset). Every action, approval, and
     rejection is recorded for the Analyst and compliance.

  9. Fallback Chain: Each agent has a preferred_fallback. If trust drops
     below threshold, routing falls through deterministically. The chain
     is: maker→mover→keeper→maker (circular).

  10. Lazy Orchestrator Init: The AgentOrchestrator is not created until the
      first crisis is triggered. This allows the app to boot and display
      the UI even if the API key is missing — the error is shown in the
      sidebar instead of crashing the app.
